# What changed from v1 to v2, and the observed failure behind each change

v1 = first complete version (prompts `classify_v1.md`, `agent_system_v1.md`), written before any model output was seen.
Official v1 run: 11 emails (`runs/v1`). The other 14 emails were then run once on v1 as a development check (not part of the v1 score).
Every change below is tied to something that actually went wrong.

| # | Email | What went wrong in v1 | Cause | Change in v2 |
|---|---|---|---|---|
| 1 | E20 (official v1) | Reply was correct (no cure claim) but the email was NOT flagged for a human. | The classifier did not set the `medical` risk flag; the rule depended on the model. | Code rule: medical or skin-reaction words in the email set the flag without the model (`code/lib/decide_route.js`). Prompt: each risk flag is now defined. |
| 2 | E21 (official v1) | Follow-up about a cracked jar was classified `return_refund` instead of `complaint`. | v1 prompt had no tie-breaker between "item problem" and "wants money back". | Prompt tie-breakers. Code rule: a damaged, leaking, wrong or missing item is routed as a complaint (High priority, human verifies) even if the model says `return_refund`. |
| 3 | E08 (dev check) | Leaking product + refund demand classified `return_refund`; the ticket got Medium priority and the wrong reason (`refund_declined`). | Same as 2. | Same as 2. Now `complaint`, High, with `angry_customer` and `public_threat`. |
| 4 | E13 (dev check) | GST invoice request classified `product_query`; the agent wrote a holding reply. Safe, but the FAQ has no answer, so no draft should be written. | v1 definition of `product_query` was too wide. | Prompt: invoices and paperwork are `other` / `business_request` (logged, flagged for a human, no draft). |
| 5 | E17 (dev check) | Influencer pitch was flagged for a human. | `other_category` values were not defined, so it was not marked `partnership`. | Prompt: each `other_category` value is defined. |
| 6 | E05 (dev check) | Draft said the team would "try their best" to deliver before the customer's trip. Policy promises nothing like that, and the ETA is the travel day. | Agent prompt did not forbid soft promises. | Agent prompt: never promise faster delivery or effort to meet a deadline; say plainly when the ETA does not fit. |
| 7 | E15 (dev check) | COD reply omitted the FAQ's "keep exact change" point. | Agent did not consult the FAQ for a COD order. | Agent prompt: when cash on delivery is mentioned, also check the COD policy. |
| 8 | E12 (official v1) | Handled correctly (declined, ticket created, nothing approved), but the instruction-like text inside the email was not flagged. | The flag depended on the model. | Code rule: text addressed to an AI or trying to override rules sets `embedded_instructions`. It never changes routing or priority. |
| 9 | E05 (first full v2 run, `runs/v2_run1`) | The Hinglish email was labelled `hi`, so the reply came in Devanagari and wrote the order ID as "केसी-1043". | The language label depended on the model; in an earlier dev run the same email was labelled correctly, so it is not stable. | Code rule: `hi` requires Devanagari script in the email, otherwise the label becomes `hinglish` (and the reverse). Agent prompt: IDs, links, names, dates and amounts are never translated or transliterated. All 25 emails were then run again (`runs/v2`). |
| 10 | E14 (second full v2 run, `runs/v2_run2`) | The draft said the customer received "Bhringraj Hair Oil 100 ml". The product is 200 ml and the customer never stated a size: an invented detail. | The agent added a size to an item it knew only from the customer's words. The scored checks did not look at sizes; I found it by reading every draft. | Code check: any product size in a draft must exist in the order or the FAQ, otherwise the draft is replaced and flagged. Agent prompt: repeat the customer's own words without adding details. |
| 11 | E01, E05, E10, E15, E23, E24 (`runs/v2_run2`) | Dates appeared as `2026-11-23`. | My own change 9 told the agent to copy dates exactly as the tool returns them. | `get_order` now also returns display dates (21 Nov 2026) and the prompt says to use them. |
| 12 | E09 (`runs/v2_run2`) | The reply contained markdown asterisks. | Nothing told the agent that replies are plain text. | Post-check strips markdown emphasis; prompt says plain text only. |
| 13 | all (`runs/v2_run2`) | `cost_usd_est` was 0 in every row. | Prices had not been set in Config. | Per-model list prices added to Config; the column is now filled. It is still an estimate from character counts. |
| 14 | E12 / E14 (third full v2 run, `runs/v2_run3`) | Two emails got the same ticket ID (`TKT-005`), so E14's ticket overwrote E12's: 8 ticket rows instead of 9. All 25 audit rows were still correct. | The LLM provider throttled and three replies took over 3 minutes. My test runner gave up waiting after 175 s and sent the next email while the slow one was still running, so two runs read the Tickets tab at the same moment and both picked the next counter value. | Ticket IDs now come from the order (`TKT-1055`), so different orders cannot collide. The runner waits up to 15 minutes and stops instead of sending the next email if one fails. The scorer now checks that every expected ticket row exists. |

Not changed: models, temperatures, the answer key, the pipeline shape.
After changes 1-8 the 10 affected emails were re-run once on the practice sheet (`runs/dev4`): 10/10 intent and 10/10 action.
Full v2 runs on the main sheet: `runs/v2_run1` (found change 9), `runs/v2_run2` (found changes 10-13), `runs/v2_run3` (found change 14), `runs/v2` (final). Anything still wrong in the final run is listed in TEST_REPORT.md section 5.
